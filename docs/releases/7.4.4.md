## What's new

### Security fix: Cross-Collection authorization bypass via Collection privacy settings

An authenticated user with access to the Wagtail administrative interface and the "change" permission to at least one Collection could change the privacy settings for a Collection they do not have access to, leading to them potentially removing access restrictions on sensitive documents. The vulnerability is not exploitable by an ordinary site visitor without access to the Wagtail admin.

Many thanks to xutao and Rajesh Murthy for reporting this issue. For further details, please see [security advisory GHSA-jm43-45cc-q9rr](https://github.com/wagtail/wagtail/security/advisories/GHSA-jm43-45cc-q9rr).

### Security fix: Formula injection via XLSX export

A vulnerability existed in Wagtail's form builder export feature and other areas where untrusted user input may be exported to XLSX format, such as reports. An attacker could insert a string value which, when exported to XLSX format and opened in an external spreadsheet application, is interpreted as a formula. The impact of this is dependent on the spreadsheet application, but may include command execution or data filtration (most likely requiring further interaction from the user opening the spreadsheet).

Note that this vulnerability is distinct from the known issue of [CSV formula injection](https://docs.wagtail.org/en/stable/contributing/security.html#formula-macro-injection-within-csv-exports), which is outside of Wagtail's scope as it depends on the spreadsheet software providing its own interpretation of the file contents that has no basis in the CSV specification. In the XLSX case, the file exported by Wagtail explicitly identifies cells as containing formulae.

For further details, please see [security advisory GHSA-g6cr-c9h3-6j2m](https://github.com/wagtail/wagtail/security/advisories/GHSA-g6cr-c9h3-6j2m).

### Security fix: Improper restriction handling on Pages admin API for ancestor pages

The internal Pages admin API allowed authenticated users to access arbitrary contents of pages which are either a direct parent of a page the user has edit permission over, or a common ancestor of multiple pages the user has edit permission over. This could allow them to retrieve data that would otherwise be unavailable to them.

The vulnerability is not exploitable by an ordinary site visitor without access to the Wagtail admin.

Many thanks to Nguyen Dang Khoi for reporting this issue. For further details, please see [security advisory GHSA-3xgh-xc8p-9h54](https://github.com/wagtail/wagtail/security/advisories/GHSA-3xgh-xc8p-9h54).

### Security fix: Stored XSS attack via third-party HTML editors

A cross-site scripting vulnerability existed in the handling of rich text input by third-party rich text editors such as wagtail-hallo which use Wagtail's legacy "Editor HTML" conversion logic. An authenticated user with edit permission over pages or snippets could submit specially-crafted rich text content through the API that bypasses Wagtail's sanitisation logic, allowing arbitrary HTML (including scripting) to be inserted into page or snippet content. Sites that use the default Draftail rich text editor are not affected.

Many thanks to ma4ter0x22 and Alberto Fernandez-de-Retana for reporting this issue. For further details, please see [security advisory GHSA-4pg7-87vv-vrh7](https://github.com/wagtail/wagtail/security/advisories/GHSA-4pg7-87vv-vrh7).
